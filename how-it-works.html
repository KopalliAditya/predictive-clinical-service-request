How Predictive Scoring Works

What the setup builds behind the scenes — the data transforms and the AI model — and how a score reaches the Clinical Service Request.

The three setup steps assemble a small pipeline in Data Cloud. Your Clinical Service Request (CSR) data is shaped by two Batch Data Transforms, an AI model learns from it and scores each request, and Copy Field Enrichment copies the score back to the CRM.

Batch Data Transforms (BDTs)

A Batch Data Transform is a Data Cloud pipeline that reads from one or more data model objects (DMOs), derives and reshapes fields, and writes the result to another DMO on a schedule. The scoring template (Step 2) creates two of them.

Training data transform

Reads your resolved Clinical Service Requests — plus any linked Diagnostic Summary and Patient Health Condition data — and for each one computes:

  • the model's features (priority, request age, type, and the diagnostic/health-condition flags and categories you turned on), and
  • the training label — whether that request was ultimately accepted.

It writes these labeled rows to the ClinicalServiceRequestTrainingData DMO. This is the history the model learns from, so it only includes requests that already have a known outcome.

Scoring data transform

Reads the Clinical Service Requests you want to score, computes the same features (but no label, since the outcome isn't known yet), and — after the model runs — the predicted score lands in the ClinicalServiceRequestScoringData DMO.

The custom filter parameters in Step 2 decide which requests each transform reads. That's why the training filter is usually narrower (resolved requests only) than the scoring filter (the open requests you want prioritized).

Both transforms run on a schedule, so as new Clinical Service Requests arrive and old ones resolve, the training data and the scores stay current.

The AI model

The template builds a predictive model in Einstein Studio (Data Cloud's model-building tool). It is a binary classification model: from the training dataset it learns the relationship between a request's features and whether it was accepted.

For every request in the scoring dataset, the model outputs a Derived Score — a likelihood, expressed on a 0–100 scale, that is used to prioritize referrals. A higher score means the model considers the request more likely to be accepted.

  • Train and Deploy (a Step 2 parameter, on by default) tells the framework to train the model and then activate it automatically.
  • Once the model reaches Active status, the scoring transform can write scores. A model that never leaves Activating usually means the training label was all one value — see Troubleshooting.
What the score is — and isn't The Derived Score reflects the likelihood a referral is accepted, for prioritizing a queue. It is not a clinical quality or acuity score. Do not use it to triage emergency cases.

Where the score ends up

The model's score lives in a Data Cloud DMO, which coordinators don't work in. Copy Field Enrichment (Step 3) copies the DerivedScore_prediction__c value from the scoring DMO onto the Referral Score field of the matching Clinical Service Request in the CRM, where referral coordinators can see and sort by it.

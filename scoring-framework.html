Step 2 — Install the Patient Access Scoring Template

Install the scoring template, choose which signals the model learns from, and confirm the training label — all from the Scoring Framework.

Open the Scoring Framework and install the template

1

From Setup, go to Scoring Framework.

2

Find and install the Patient Access Scoring template.

Template name The template's label is Patient Access Scoring (internal name PatientAccessScoring). Depending on your release and org, the Scoring Framework list may show it under the Referral Management grouping — it's the one described as "Predictive scoring for Clinical Service Request prioritization using Health Cloud DMOs."
3

Step through the install wizard, setting the parameters below. Every parameter has a sensible default — for a standard referral-acceptance model you can accept all defaults and only set the Data Space.

Fastest path Accept every default, select your Data Space, and install. The defaults are tuned for referral acceptance. Only change a parameter when you have a specific reason — the sections below tell you when.

How the parameters are organized

The parameters fall into three groups:

  • Data Space — where the model reads and writes.
  • Features — which signals the model is allowed to learn from.
  • Filters and the Target Variable — which records to score and what outcome to predict.

Data Space

Data Space Optional
Default: default

The Data Cloud data space the model reads its DMOs from and writes its scoring data into. Set this to the same data space you deployed the data kit into in Step 1. If you use a single default data space, leave it as default.

Features — which signals the model learns from

Each feature is a toggle. Turning one on tells the model it may use that signal when learning to predict acceptance. Priority and request age are always included and have no toggle.

Include Clinical Service Request Type Default on
Default: true

Include the Clinical Service Request Type as a feature. Keep this on if your referrals vary by type and type influences acceptance.

Include Has Diagnostic Summary Default on
Default: true

Include a flag for whether the request links to a Diagnostic Summary. This reads from the request's own lookup, so it adds signal even when you haven't mapped Diagnostic Summary data. Safe to leave on.

Include Has Patient Health Condition Default on
Default: true

Include a flag for whether the request links to a Patient Health Condition. Also reads from the request's own lookup, so it adds signal even when Patient Health Condition data isn't mapped. Safe to leave on.

Include Diagnostic Summary Category Default on, data-dependent
Default: true

Include the Diagnostic Summary Category as a feature. Requires Diagnostic Summary data to be mapped (via the data kit's Diagnostic Summary stream). If that data is absent the feature is simply empty and has no effect — it won't break the install. Turn it off only to simplify the model when you know you'll never map that data.

Include Patient Health Condition Severity Default on, data-dependent
Default: true

Include the Patient Health Condition Severity as a feature. Requires Patient Health Condition data to be mapped. If absent, the feature is empty and has no effect. Same guidance as above.

Custom filters — which records to score

All three filter parameters are optional SQL expressions applied to the Clinical Service Request source. Leave them blank to score every request. Use them only when you want to narrow the population — for example, to a single region or line of business.

Custom Filter logic Optional
Default: (blank)  ·  applies to both training and scoring

A single SQL filter applied to both the training and the scoring data transforms. Use this when you want the same population for training and scoring. Example: ssot__ClinicalServiceRequestType__c = 'Specialist Referral'.

Custom Filter logic (Training) Optional, advanced
Default: (blank)  ·  applies to training only

A SQL filter applied only to the training data transform. Use together with the scoring filter below when you deliberately want to train on a different population than you score (for example, train on completed historical requests only).

Custom Filter logic (Scoring) Optional, advanced
Default: (blank)  ·  applies to scoring only

A SQL filter applied only to the scoring data transform. Pair with the training filter above. For example, score only open requests while training on historical ones.

Use one filter strategy, not both Either set the single Custom Filter logic (same population for both), or set the separate Training and Scoring filters. Mixing a global filter with the split filters makes the effective population hard to reason about.

Target Variable — the outcome the model predicts

This is the most important parameter to understand, even though you'll usually keep the default. It defines the training label — the outcome the model learns to predict.

Target Variable details Optional (defaulted)
Default: referral acceptance (Binary, Maximize)

Defines the label the model learns. The condition is a SQL expression evaluated on the Clinical Service Request source; it must return the numeric outcome value. The default predicts referral acceptance. Override it only for a different Clinical Service Request use case.

The default is made up of these sub-fields:

Sub-fieldDefaultMeaning
LabelDerived ScoreDisplay name of the predicted outcome.
FieldDerivedScore__cThe field that holds the derived training outcome.
TypeBinaryThe outcome is yes/no (accepted vs. not).
Success1Value that represents the positive outcome (accepted).
Failure0Value that represents the negative outcome (not accepted).
GoalMaximizeThe model optimizes for the success outcome.
ConditionThe SQL that computes the outcome (below).

The default condition classifies a request as accepted (1) when it is marked accepted or has reached an Active/Completed status:

CASE
  WHEN ssot__IsAccepted__c = 1 OR ssot__IsAccepted__c = true THEN 1
  WHEN ssot__ClinicalServiceRequestStatus__c IN ('Active', 'Completed') THEN 1
  ELSE 0
END
The label depends on IsAccepted being a real boolean The condition compares ssot__IsAccepted__c to true/1. This only matches if the data kit mapped acceptance into the DMO as a boolean (Step 1 does this). If acceptance arrives as text, the comparison never matches, every row gets label 0, and the model can hang in Activating. See Troubleshooting.

Parameters you don't set

A couple of parameters are managed by the framework and shouldn't be changed: Train and Deploy (installs and trains the model automatically) and an internal test flag used only by functional tests. Leave both at their defaults.

Finish and verify

4

Complete the wizard. The template installs the model definition, data transforms, and the scoring container, then begins training.

5

Confirm the model reaches Active status. A model that stays in Activating for a long time usually means the training label is all one value — see Troubleshooting.

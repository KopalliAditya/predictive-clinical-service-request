Troubleshooting

Find the installation phase that failed, then apply the matching fix.

The installation phases

When you install the template, it runs as a chain of phases in this order. Each phase depends on the one before it, so identify the phase that failed first — the fix depends on which one it is.

Phase 1 — Readiness check fails

Symptom: the install shows a readiness failure or warning before it creates anything.

MessageCause & fix
Clinical Service Request DMO is not mapped The data kit wasn't deployed, or its streams haven't run, so the DMO is missing Id, ClinicalServiceRequestPriority, or ClinicalServiceRequestStartDate. Complete Step 1 and confirm the DMO is mapped.
Not enough records The Clinical Service Request DMO has fewer than 400 rows. Confirm the streams ran and the DMO is populated.
Needs both accepted and not-accepted requests (warning) Every request has the same outcome, so the model can't learn to distinguish them. This warns but does not block install. Populate IsAccepted, or let requests move through Active/Completed statuses, so the data has a mix of outcomes.

Phase 2 — Training data transform (BDT) fails

Symptom: the install fails at the data transform step, or the ClinicalServiceRequestTrainingData DMO is empty after install.

Cause: the training transform reads specific fields from the Clinical Service Request, Diagnostic Summary, and Patient Health Condition DMOs. If one of those fields isn't mapped, the transform can error or produce empty output.

Fix: confirm every field the transform reads is mapped — the full list is in Step 1, Verify the DMO field mappings. The required fields are on the Clinical Service Request DMO:

  • ssot__Id__c, ssot__ClinicalServiceRequestPriority__c, ssot__ClinicalServiceRequestStartDate__c
  • ssot__ClinicalServiceRequestStatus__c, ssot__ClinicalServiceRequestType__c, ssot__IsAccepted__c
  • ssot__DiagnosticSummaryId__c, ssot__PatientHealthConditionId__c

The Diagnostic Summary Category and Patient Health Condition Severity fields are optional — if they're unmapped the transform still runs, and those features are just empty.

Phase 2/5 — Field mapping is wrong (the IsAccepted type trap)

Symptom: the transform runs without error, but the training label comes out all one value — which later shows up as a model stuck in Activating (see below).

Cause: the training label compares ssot__IsAccepted__c = true. If acceptance is mapped into the DMO as text ("true"/"false") instead of a boolean, the comparison never matches and every row gets label 0.

How to confirm: count the accepted rows on the DMO. A zero count when you know some requests were accepted means the field is text, not boolean:

-- via the /ssot query API
SELECT COUNT(*) FROM ssot__ClinicalServiceRequest__dlm
WHERE ssot__IsAccepted__c = true

Fix: the Health Cloud Scoring data kit maps acceptance to a boolean with a formula field. Confirm that mapping is present; if not, redeploy the current data kit (Step 1) and Stop/Start the sync.

Why text vs. boolean happens The Salesforce connector can ingest a CRM boolean as text in the DLO. The data kit's formula field (IF(IsAccepted == 'true', true, false)) normalizes it back to a boolean so the label matches. A null or unexpected value resolves to false.

Phase 4 — Model training warns or produces a single-class model

Symptom: training completes with a warning, or the model predicts the same outcome for everything.

Cause: the training label has only one class — either the mapping trap above, or the underlying data genuinely has no mix of accepted and not-accepted requests.

Fix: resolve the mapping trap first, then confirm the data has both outcomes (the Phase 1 label-balance check). Retrain after fixing.

Phase 5 — Model stuck in "Activating"

Symptom: the model definition version sits in Activating and never reaches Active.

Likely cause: the model trained on an all-one-value label (the mapping trap in Phase 2/5), so there's no usable two-class model to activate.

Fix: fix the IsAccepted mapping, confirm a mix of outcomes, and reinstall/retrain so the model can activate.

Phase 6 — Scoring data transform produces no scores

Symptom: the model is Active, but the ClinicalServiceRequestScoringData DMO has no rows.

Cause: the scoring transform only runs when Train and Deploy is on, and it reads the same Clinical Service Request DMO fields as training. A custom scoring filter that's too narrow can also exclude every record.

Fix: confirm Train and Deploy was left on (Step 2), the source DMO fields are mapped, and any Custom Filter logic (Scoring) isn't filtering everything out.

Phase 7 — No "Referral Score" field on the Clinical Service Request

Symptom: there's nowhere for the score to land; querying for the field returns nothing.

Cause: the Copy Field Enrichment target mapping was never created, so the field that receives the score doesn't exist.

Fix: create the CFE with target Clinical Service Request mapped to the Referral Score field — see Step 3, Part A. Verify with:

SELECT QualifiedApiName FROM FieldDefinition
WHERE EntityDefinition.QualifiedApiName = 'ClinicalServiceRequest'
  AND (QualifiedApiName LIKE '%Score%' OR QualifiedApiName LIKE '%Referral%')

Phase 7 — Scores never appear on the CSR (field exists, count stays 0)

Symptom: the Referral Score field exists and the scoring DMO has rows, but no Clinical Service Request ever gets a score.

Cause: the writeback integration user lacks Health Cloud access, so the update to the Clinical Service Request doesn't happen.

Fix: complete Step 3, Part B — enable Manage Health Cloud on sfdc_a360 and assign the Health Cloud Platform permission set license to the cloud@ integration user — then Stop/Start the sync.

A Scoring Framework configuration is stuck and can't be deleted

Symptom: a model configuration shows only a View action (no Delete) while it's in Activating.

Cause: configurations can't be deleted while activating.

Fix: resolve the activation first (often the label issue above, so it reaches Active), then delete it. If it stays wedged, open a support case rather than forcing deletion.

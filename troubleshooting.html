Troubleshooting

Common setup failures and how to resolve them.

Model stuck in "Activating"

Symptom: After Step 2, the model definition version sits in Activating and never reaches Active.

Likely cause: the training label is all one value. The default Target Variable condition compares ssot__IsAccepted__c = true. If the data kit mapped acceptance into the DMO as text ("true"/"false") instead of a boolean, that comparison never matches, every row gets label 0, and the model can't learn a two-class outcome.

How to confirm: query the accepted-row count on the DMO. If it's zero even though you know some requests were accepted, the field is text, not boolean:

-- via the /ssot query API
SELECT COUNT(*) FROM ssot__ClinicalServiceRequest__dlm
WHERE ssot__IsAccepted__c = true

Fix: make sure the Clinical Service Request data stream maps acceptance into the DMO's boolean IsAccepted field. The Health Cloud Scoring data kit does this with a formula field that converts the raw value to a boolean. If your deployed stream doesn't have that mapping, redeploy the current data kit (Step 1), then Stop/Start the sync.

Why text vs. boolean happens The Salesforce connector can ingest a CRM boolean as a text value in the DLO. The data kit's formula field (IF(IsAccepted == 'true', true, false)) normalizes it back to a boolean so the label condition matches. A null or unexpected value resolves to false, which is the correct default.

Readiness check fails: "Clinical Service Request DMO is not mapped"

Symptom: Step 2 install blocks with a message to map the CSR DMO.

Cause: the data kit either wasn't deployed, or its streams haven't run, so the ClinicalServiceRequest DMO has no rows (or is missing Id, ClinicalServiceRequestPriority, or ClinicalServiceRequestStartDate).

Fix: complete Step 1, confirm the streams ran, and confirm the DMO has rows before retrying Step 2.

Warning: "needs both accepted and not-accepted requests"

Symptom: install succeeds but warns that the label has only one class.

Cause: every request in the DMO is either all-accepted or all-not-accepted, so the model can't learn to distinguish them. This does not block install.

Fix: populate IsAccepted on your requests, or let requests progress through Active/Completed statuses, so the data contains a mix of outcomes. Then retrain.

No "Referral Score" field on the Clinical Service Request

Symptom: there's nowhere for the score to land; querying for the field returns nothing.

Cause: the Copy Field Enrichment target mapping was never created, so the field that receives the score doesn't exist.

Fix: create the CFE with target Clinical Service Request mapped to the Referral Score field — see Step 3, Part A. Verify with:

SELECT QualifiedApiName FROM FieldDefinition
WHERE EntityDefinition.QualifiedApiName = 'ClinicalServiceRequest'
  AND (QualifiedApiName LIKE '%Score%' OR QualifiedApiName LIKE '%Referral%')

Scores never appear on the CSR (field exists, count stays 0)

Symptom: the Referral Score field exists and the model is Active, but no CSR record ever gets a score.

Cause: the writeback integration user lacks Health Cloud access, so the update to the Clinical Service Request doesn't happen.

Fix: complete Step 3, Part B — enable Manage Health Cloud on sfdc_a360 and assign the Health Cloud Platform PSL to the cloud@ integration user — then Stop/Start the sync.

A Scoring Framework configuration is stuck and can't be deleted

Symptom: a model configuration shows only a View action (no Delete) while it's in Activating.

Cause: configurations can't be deleted while activating.

Fix: resolve the activation first (often the label issue above, so it reaches Active), then delete it. If it stays wedged, open a support case rather than forcing deletion.
